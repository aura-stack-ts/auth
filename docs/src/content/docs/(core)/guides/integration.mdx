Aura Auth is a **framework-agnostic and modular authentication system** designed for TypeScript applications. Its core is built on Web Standards, including the [`Request`](https://developer.mozilla.org/en-US/docs/Web/API/Request) and [`Response`](https://developer.mozilla.org/en-US/docs/Web/API/Response) interfaces, and supports OAuth 2.0 and OpenID Connect (OIDC).

Because Aura Auth uses standard HTTP requests and responses, it can be integrated with JavaScript runtimes and frameworks that support server-side request handling.

For reference implementations, see [Aura Auth Apps](https://github.com/aura-stack-ts/auth/tree/master/apps).

This guide explains the architecture of Aura Auth integrations and how to create a dedicated integration package for a framework or library.

## Architecture

### Core Package

The `@aura-stack/auth` package provides the core `createAuth` function and authentication logic. It returns an `AuthInstance` with the following properties:

- `handlers`: HTTP handlers for authentication endpoints.
- `api`: Server-side API functions, including `signIn`, `signOut`, and `getSession`.
- `jose`: JWT and cryptographic utilities.
- `session`: Session management utilities.

The core package handles authentication independently of any specific framework. Integrations connect this functionality to a framework's request lifecycle, routing system, and context APIs.

### Integration Packages

Integration packages provide framework-specific adapters around the core authentication functionality. Depending on the framework, an integration may:

1. Wrap the core `createAuth` function with framework-specific configuration or utilities.
2. Provide handler adapters, such as `toHandler`, to connect Aura Auth handlers to the framework's request lifecycle.
3. Expose middleware or plugins, such as `withAuth`, to make session data available in the framework's context.
4. Export framework-specific types while preserving the core API's type information.

Not every integration requires all these utilities. The implementation should follow the framework's conventions and expose only the functionality that is useful for that framework.

### Generic Types

The core `createAuth` function accepts generic type parameters for the identity and sign-up schema:

```ts
createAuth<Identity, SignUpSchema>(
  config: AuthConfig<Identity, SignUpSchema>,
)
```

- `Identity` extends `Identities` and defines the application's identity structure.
- `SignUpSchema` extends `SchemaTypes` and defines the sign-up validation schema. Supported schema libraries depend on the core package's current type definitions.

A dedicated integration should preserve these generic parameters when wrapping `createAuth` so applications retain type inference and type safety.

## Creating a Dedicated Integration Package

For integrations that require framework-specific behavior or are intended for community distribution, use the existing integration packages as implementation references.

<Steps>
  <Step>
    ## Scaffold the Integration

    Use the `create:integration` command to scaffold a package from the integration template:

    ```bash
    pnpm create:integration --name my-framework
    ```

    The scaffold command is intended to:

    - Copy the integration template into `packages/my-framework`.
    - Create the initial package structure.
    - Configure TypeScript and build tooling.

  </Step>
  <Step>
    ## Sync Core Modules

    From the new package directory, run the module synchronization script:

    ```bash
    cd packages/my-framework
    pnpm sync:modules
    ```

    The script synchronizes the shared modules required by the integration. These may include:

    - `oauth`: OAuth provider implementations.
    - `identity`: Identity schema types and utilities.
    - `crypto`: Cryptographic utilities.
    - `shared`: Shared utilities.
    - `cookies`: Cookie management utilities.

    If the script manages package exports, verify that the required modules are exported and that the resulting package builds correctly.

  </Step>
  <Step>
    ## Implement a Framework-Specific `createAuth`

    Create a framework-specific `createAuth` wrapper that delegates authentication configuration and initialization to the core implementation.

    The wrapper should:

    1. Preserve the core generic parameters, including `Identity` and `SignUpSchema`.
    2. Pass the authentication configuration to the core `createAuth` function.
    3. Add framework-specific utilities where necessary.
    4. Return an instance that preserves the core `AuthInstance` API and exposes the integration's additional utilities.

    The implementation will vary by framework. Keep the wrapper thin and avoid duplicating authentication logic that already belongs to the core package.

  </Step>
  <Step>
    ## Define Instance Types

    Define the return type of the framework-specific `createAuth` function. It should preserve the core instance's types and describe any additional framework-specific properties, such as:

    - Handler adapter signatures.
    - Middleware or plugin signatures.
    - Framework-specific request or context types.

    Export the integration's public types from an appropriate entry point. Re-export core types when they are part of the intended public API.

  </Step>
  <Step>
    ## Implement a Handler Adapter

    Implement a handler adapter that connects the framework's request lifecycle to Aura Auth's Web Standard `Request` and `Response` interfaces.

    The adapter should:

    1. Accept the framework's request or context object.
    2. Obtain or construct a standard `Request`.
    3. Pass the request to the appropriate Aura Auth handler.
    4. Return the resulting `Response` in the format expected by the framework.

    Prefer passing through native `Request` and `Response` objects when the framework supports them. If conversion is required, preserve relevant request data, headers, cookies, and response semantics.

  </Step>
  <Step>
    ## Implement Middleware or a Plugin

    If the framework supports middleware or plugins, consider providing a utility that exposes session information to route handlers or other parts of the application.

    A typical implementation should:

    1. Accept an initialized auth instance.
    2. Retrieve session information through `api.getSession`.
    3. Attach the session to the framework's request context using its established middleware or plugin conventions.
    4. Define explicit behavior for missing sessions and errors.

    Treat an unauthenticated request separately from an unexpected error where the framework's API permits it. Set the session to `null` only when that matches the intended contract, and avoid silently hiding failures that should be reported or logged.

  </Step>
  <Step>
    ## Export the Public API

    Create the package entry point and export the supported integration API. For example:

    ```ts
    // packages/my-framework/src/index.ts
    export { createAuth } from "./createAuth"
    export type {
      User,
      Session,
      AuthConfig,
      AuthInstance,
    } from "@aura-stack/auth/types"
    ```

    Adjust the imports and exported types to match the actual package structure and the public types available in the core package. Prefer stable public entry points over internal module paths.

  </Step>
  <Step>
    ## Add an Example Application

    Add an example application under `apps/` to demonstrate installation, configuration, and use of the integration.

    For example:

    ```text
    apps/
    └── my-framework/
        ├── src/
        │   ├── lib/
        │   │   ├── handler.ts
        │   │   └── with-auth.ts
        │   └── index.ts
        ├── package.json
        └── tsconfig.json
    ```

    Adapt the structure to the framework's conventions. The example should demonstrate how to configure Aura Auth, register its handlers, and access session information where applicable.

  </Step>
</Steps>

## Return Object Requirements

A framework-specific `createAuth` wrapper should preserve the core instance's public API.

At a minimum, this means retaining the core properties required by the integration, such as:

- `handlers`: Authentication HTTP handlers.
- `api`: Server-side authentication and session functions.
- `jose`: JWT and cryptographic utilities, if exposed by the core instance.
- `session`: Session management utilities, if exposed by the core instance.

The exact properties should match the `AuthInstance` type exported by the version of `@aura-stack/auth` being integrated. Framework-specific utilities should extend the core API rather than replace or unintentionally narrow it.

## Best Practices

1. **Preserve generic types.** Carry `Identity` and `SignUpSchema` through the wrapper and its return type to maintain type inference.
2. **Keep the integration thin.** Delegate authentication logic to the core package and focus on framework-specific request handling and context integration.
3. **Re-export public types deliberately.** Expose the core types consumers need without depending on unstable internal modules.
4. **Document framework-specific behavior.** Use JSDoc and integration documentation to explain added utilities, expected inputs, and error handling.
5. **Provide a working example.** Include an example application that demonstrates the integration's main use cases.
6. **Test the adapter and middleware.** Cover request and response conversion, session retrieval, unauthenticated requests, and error handling.
7. **Keep synchronized modules up to date.** Run `pnpm sync:modules` after core changes when the integration relies on synchronized modules, then verify the generated code, exports, and build.
8. **Verify runtime compatibility.** Test against the runtimes and framework versions the integration claims to support.
